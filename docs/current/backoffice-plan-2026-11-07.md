# 낭만한줄 운영 관리 화면 — 1차 구현

후속 요청에 따라 아래 최소 구성을 로컬에 구현했다. 관리자 페이지는 `/office/orders`다. 실제 운영 데이터는 GitHub에 포함하지 않는다.

## 필요한 이유

계좌이체를 확인해 제작 키를 전달하는 상품이므로, 고객 회원가입 여부와 관계없이 대표가 주문과 키를 관리하는 백오피스는 필요하다. 고객은 가입 없이 이용하고 운영자만 로그인하는 방식으로 시작할 수 있다. 직원들이 대화하는 AI 사무실과 고객 주문 관리 화면은 목적이 다르다.

## 현재 있는 것

- 로컬 관리자 인증과 입금 확인 후 5,000원 제작 키 발급.
- 같은 발급 요청을 다시 눌러도 새 키를 중복 발급하지 않는 보호.
- 주문별 생성 원본·그림·수정 이용 상태와 작업 진행 기록의 서버 파일 보관.

새 백오피스에는 주문 목록·검색, 제작 상태·그림 완료 수, 고객 별칭·운영 메모, 키 확인·재발급·중지, 최근 관리 이력을 구현했다. 재발급은 같은 주문의 접근 키만 교체하며 기존 작품과 사용 횟수는 유지한다. 진행 중 주문의 키 변경은 차단한다. 전체 데이터 삭제와 클라우드 저장소 전환은 아직 구현하지 않았다.

## 현재 화면과 후속 범위

| 화면·기능 | 대표가 확인하거나 처리할 일 |
| --- | --- |
| 주문 목록 | 주문번호, 고객 별칭, 입금 확인일·금액, 현재 상태를 검색 |
| 키 발급·관리 | 입금 확인 후 발급, 전달 여부 기록, 미사용·사용·중지 상태 확인 |
| 제작 상태 | 글 생성 여부, 그림 완료 수/18장, 진행·완료·중단 상태 확인 |
| 오류 지원 | 현재 제작 상태와 중단 여부 확인. 재개는 기존 동화 제작 화면에서 수행하며 관리자 화면은 새 유료 제작을 자동 실행하지 않음 |
| 키 재발급·중지 | 같은 주문의 접근 키만 교체. 이미 사용한 제작 횟수와 결과는 유지하고 이전 키는 중지 |
| 데이터 관리 | 현재 별칭·메모와 관리 이력 저장. 전체 보관본 삭제·삭제 요청 처리는 후속 범위 |

첫 버전은 주문 목록과 상세 화면 두 개면 충분하다. 복잡한 직원 권한·통계·자동 입금 연동은 실제 주문이 늘어난 뒤 추가할 수 있다.

## 처음부터 지킬 운영 기준

- 고객 회원가입은 필수가 아니다. 주문번호와 제작 키로 연결하되 운영자 로그인은 별도로 둔다.
- 처음에는 별칭과 주문번호 등 필요한 최소 정보만 관리한다. 실제 이름·연락처 등을 추가로 수집하려면 목적과 보관 방식을 먼저 정한다.
- 키를 다시 발급해도 새 상품을 무료로 하나 더 만드는 것으로 처리하지 않는다. 기존 결과와 사용 횟수를 같은 주문에 유지한다.
- 그림은 실제 완료 기록을 확인한 뒤 재개한다. 요청 실패만 보고 새 키나 새 제작을 무조건 지급하지 않는다.
- 고객 사연·주문 파일·실제 발급 키·관리자 비밀번호·API 키는 GitHub에 저장하지 않는다. GitHub에는 프로그램 코드와 가짜 테스트 자료·명세만 저장한다.
- 공개 고객 화면에 직원 사무실이나 관리 API를 열지 않는다. 지금 로컬 관리자 화면을 그대로 인터넷에 노출하는 방식으로 전환하지 않는다.
- 서버 보관본, 고객 브라우저의 책장, 고객이 내려받은 파일은 별개다. 서버 기록 삭제가 모든 복사본 삭제를 의미한다고 안내하지 않는다.
- 공개 운영 전에는 주문과 결과를 지속 보관하는 저장소, 백업·복구, 관리자 접근 보호를 갖춘다. 현재 로컬 파일 방식의 온라인 전환은 별도 구현이다.

## 개발 순서

1. 읽기 전용 주문 목록·상세·제작 진행 상태.
2. 입금 확인·기존 키 발급 화면 연결과 처리 기록.
3. 키 중지·동일 주문 재발급, 오류 복구 안내.
4. 보관·삭제 요청 처리와 백업·복구.

## 검증

모의 주문으로 관리자 인증·미인증 차단, 발급·검색·메모 저장, 목록의 전체 키 숨김, 재발급 후 이전 키 차단과 기존 작품·사용 횟수 보존, 키 중지, 진행 중 주문 변경 차단, 로그아웃과 PC·모바일 배치를 확인했다. 실제 고객 데이터나 추가 유료 AI 호출은 사용하지 않았다.
